# 兩階段一次性汰除 `lib/database`、收編 `lib/poc`

這份報告只講**方向與精神**,不寫實作細節——細節留給實際動手的那次對話讀完後自己想。
它要回答的是:「怎麼一次性把舊 `src/lib/database` 換成 `poc`,而且是照 `poc` 本來的精神去換。」

---

## 精神:不是搬介面,是改用「可組合的積木」

`poc` 對外的介面**刻意跟舊版不一樣**,而且(理論上)更乾淨。關鍵差別在於:

舊 `database/` 給的是一組**預烤好的 facade 函式**——像 `queryImages(params, overrides)`,
那個 `overrides` 參數其實是為了塞各種頁面特例硬加的旁門。每冒出一個新需求,就得回去替 facade 加參數。

`poc` 給的不是成品,是**正交的積木**:能 `fromSearchParams` / `.with()` / `toSearchParams` 的查詢值物件、
注入 `db` 就能用的 `Query` / `Mutation`、以及可以直接 `switch` 的 `Result` 錯誤資料。
它的主張是:**呼叫端自己用這些積木「組合」出它要的業務**——而且同一套積木,也能組出未來還沒出現的業務,
不必再回頭動介面本身。

> `plan/db-module.md` 開頭那段示意(`new Query(db)`、`ImageQuery.fromSearchParams(...)`、
> `Result` 檢查、`errorToHttp`)其實已經在示範這個組合精神。這次遷移,就是把那段示意變成全 app 的現實。

所以這次不是「保留舊簽章、底層偷換引擎」,而是**每個呼叫端都改用新積木重新表達自己的需求**。
介面不一樣是設計,不是要被藏起來的成本。

---

## 為什麼分兩階段

把「換引擎 + 改呼叫端」和「搬檔案 + 改命名」拆開,是因為它們風險等級完全不同:

- **第一階段**做有意義、有風險的事:刪掉整個 `lib/database`,讓所有呼叫端改吃 `poc`,
  並補上 `poc` 對外本來就規畫、但還沒寫的邊界件。但**先不動 `src/lib/poc/` 的位置**——
  這樣這一階段的 diff 就是乾淨的一句話:「`database` 沒了,大家改指向 `poc`,`poc` 長出邊界件」,好審、好回退。
- **第二階段**才做純結構收尾:把 `poc/*` 提升到 `lib/*`、去掉命名裡的 `poc` 痕跡。**行為零變化**,
  好驗(測試照綠、app 照跑即可)。

兩件事混在一起改,出問題會分不清是「組合邏輯錯了」還是「路徑搬錯了」;拆開就各自單純。

---

## 第一階段:汰除 `lib/database`,呼叫端改用 `poc` 的組合式介面

目標:`src/lib/database/` **整個刪除**;所有呼叫端(15 個 server 端 + 3 個 client 端 + 一票純型別引用)
改成用 `poc` 的積木自行組合;`poc` 對外補齊本來規畫、但目前還缺的邊界件。位置保持在 `src/lib/poc/`。

這一階段的核心是「示範組合」,幾個代表性的例子:

- **特例參數消失,變成普通組合。** 舊的 compare「隨機兩張」、editor「不分頁」是靠 `queryImages` 的
  `overrides` 特例參數達成的。新做法是:route 自己把查詢值物件建起來,再 `.with()` 調整它要的那一項
  (換個排序、把分頁關掉),交給 `Query`。同一種手法,未來任何頁面要任何組合都這樣拼,不必再替介面開後門。

- **錯誤從「丟例外」變成「一筆資料」。** 舊 mutation 失敗是 throw 一個帶神秘 `status` 的例外,route 得 `try/catch`。
  新 mutation 回一個 `Result`:成功就取 `data`,失敗就拿到一個可辨識的錯誤物件,route 依它的種類組出對應的 HTTP 回應。
  錯誤變成可以被組合的資料,而不是要被接住的意外。

- **「要 facet 還是要清單」用選方法表達,不用旗標。** 舊的標籤查詢靠一個 options 旗標區分「篩選 facet」
  和「編寫用的獨立清單」。新做法是這根本是兩個不同的東西:呼叫 `facets(...)` 還是 `tags(...)` 本身就是意圖,
  沒有「空 scope 還是沒 scope」的模糊。

- **補齊 `poc` 規畫中的邊界件。** `poc` 刻意把某些「邊界上才組裝」的東西留到接上時才寫——
  最明顯的是 `errorToHttp`(把 `Result` 的錯誤種類映成 HTTP 狀態碼),`plan/db-module.md` 說它「住在 route 端」
  但目前全庫還沒有。這一階段要把這類邊界件一次補好、讓呼叫端能乾淨地組合。

**第一階段結束時的樣子**:`lib/database` 不存在了;每個呼叫端都用 `poc` 的積木表達自己的業務;
`poc` 對外的邊界件齊了;`src/lib/poc/` 目錄本身原封不動。

---

## 第二階段:去 `poc` 化(結構與命名收尾)

第一階段之後,`poc` 已經是唯一的資料庫模組,只是它還頂著「poc」這個過渡期的名字待在 `src/lib/poc/`。
第二階段把這層過渡痕跡清掉,**不改任何行為**:

- **把 `src/lib/poc/*` 提升到 `src/lib/*`**(`database` / `query` / `query-spec` / `mutation` 各就各位),
  隨之更新呼叫端的 import 路徑,以及 `testing-scripts/` 裡的 import 路徑。
- **清掉命名裡的「poc」痕跡。** 例如單例目前為了跟舊版並存,叫的是 `globalThis.__pocDb` 這種帶前綴的名字;
  舊版沒了之後,這類前綴就該還原成乾淨的名字。連同註解、路徑、識別字裡殘留的「poc」字樣一併收掉。

因為這一階段是純搬移與改名,驗收標準很單純:**既有測試照樣全綠、app 照樣能跑**,就代表沒動到行為。

---

## 驗證要點

- **第一階段**(有行為變化):跑 `testing-scripts/run-all.mjs` 守住引擎層。並完成 `plan\db-migration-stage1-manual-test.md`
- **第二階段**(無行為變化):測試全綠 + app 能跑即可;若有東西壞了,幾乎一定是 import 路徑或改名沒收乾淨。
