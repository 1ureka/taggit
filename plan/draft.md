# 2.0.0 重寫大部分的 lib，實現標準 SSR Faceted Search

提出整體應用在業務邏輯上的新架構，使其更容易模組化與局部更新，且須考慮到未來的可測試性。同時，新的實作要改成實現 Bitmap Index 基礎建設，以及修改對應的 api 入口，並說明前端實現 Faceted 搜尋，完全刪除原有的倒排索引機制，因此還得考慮到 ID 與序號的問題。最後是目前 JSON 只儲存圖片ID => 圖片元資料，我希望在不影響舊 db.json 的情況下，也能為標籤本身有元資料的框架(JSON 格式修改、types.ts 等等)，可先初步實現控制標籤是否預設隱藏，預設為不隱藏，所謂隱藏代表只要有該標籤的圖片，在查詢時只要不帶有該標籤，即便有其他標籤命中，也不會出現該圖片，不篩選時自然也是不會出現該圖片 (你不需考慮前端在哪裡設定標籤本身的元資料，只要後端能夠支援即可)

以上都不包括實際代碼修改，你要做得是根據工作量與規劃，寫至少一份 plan/index.md ，並根據情況多寫幾個 md，用於說明可行性與實作規劃

## Tag Cache 概念刪除

由於這是個人本地或局域網使用，多工的需求在實際使用的過程中幾乎沒有，我認為當前 `createSWR` 幾乎是不需要的，尤其是它會與計畫的 facade 搜尋有很大的衝突，因此我希望完全刪除。同時注意到，我在資料流動上其實更喜歡 SSR (page load)，而不是 GET 請求，因此更好的做法應該是 database 模組有 server 端可呼叫的 queryTags 等方法或函數，然後在 page load 直接使用，篩選、查詢時也都是透過其做 SSR，也由於其刪除，client/cache.ts 應該也能完全刪除

## 業務透過資料夾模組化、確立職責、使未來可局部測試

目前主要區分業務邏輯的方式只有 client, server，其中該專案的兩大要件與幾個模組混雜在一起，比如 database, image process, collection manage 等等，我認為這樣下去難以維護與擴展，因此需要大幅重寫，不只是重構，我認為應該提取出 database, image 兩大業務模組，前者處理 json 到記憶體元資料的管理(比如查詢、新增)與溝通(比如 params 構建與分析)，後者處理圖片相關的壓縮、溝通(比如定義怎樣構建 imgSrc)，前者不在意是不是有實際圖片，id 是檔名這件事它不在意，database 只在意 id 是獨一無二的，它只在意在給定的 collection json file 下，怎樣處理，後者不在意這張圖片到底在 json 有沒有紀錄、怎樣紀錄，它只在意在給定的 collection 下，怎樣找到圖片、處理圖片、讓前端要求與溝通等

另外，會注意到由於 database 在新增圖片紀錄時，需要儲存元資料，這導致耦合，我目前的想法是透過更上層的 api (比如 POST) 來做耦合，而不要影響 database

其中應該也會注意到 collection 其實也是一個模組，它的職責是管理當前是哪個 collection，處理 root 等，它不在意 json 對不對，但它會知道目錄是否存在，有沒有 json 與 /images 資料夾，要不要初始化結構等

因此應該會有三大模組

## 業務模組入口為 client.ts + server.ts

我會希望能夠系統化的設計模組邊界，我希望最終的介面一定是兩個檔案，以 database 來說，server 肯定包括查詢、新增等介面，但同時 database 還包括 params 這種職責，你可能會想說這不算 shared 嗎? 我的看法是盡量不要，保持 server + client，比如 server 介面的查詢可以直接吃 URLParams 然後介面本身會自行呼叫 params 模組解析，client 則會有特化給前端使用的 build 與 parse 等，甚至是物件化等，看前端大部分是怎樣用，就在 client.ts 特化並包裝。以 image 來說，server 包括處理圖片、轉檔、讀取元資料等等，client 則是構建 imgSrc (也就是所謂定義溝通) 等

其中 collection 我不確定是不是不需要 client.ts，又或者可以考慮將當前只有用於 pathHistory 的 localStorage 相關功能視作 collection 模組也不錯，這樣未來要轉成也存到 server.json 也更容易看出來
