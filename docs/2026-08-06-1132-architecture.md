## 一、這是什麼程式

本機執行的個人圖片管理工具。SvelteKit + `adapter-node`，跑在使用者自己的機器上，
**沒有帳號、沒有多使用者、沒有遠端資料庫**。

設計上的核心約束是「雲端同步友好」：程式只是一層殼，資料全留在使用者指定的收藏目錄裡。

```
<收藏目錄>/
├── images/      原始圖片檔案（程式不主動更動內容與檔名）
└── db.json      唯一的紀錄檔（標籤、評分、狀態全在這）
```

除此之外會落地的只有專案根目錄的 `server.json`（記住收藏目錄路徑）。
資料庫索引與縮圖**只存在於記憶體**，重啟即重建。

### 使用流程

```
上傳 / 直接丟檔案  →  images/ 有檔案、db.json 沒紀錄  ── 這就是「暫存區」
        │
        │ /staged 加標籤評分後提交（或用 JSON 批次匯入）
        ▼
   db.json 有紀錄  ── 這就是「已提交」
        │
        ├── /            瀑布流瀏覽 + 詳情
        ├── /player      全螢幕無限捲動播放
        ├── /compare     並排比較
        ├── /committed   編輯名稱／標籤／評分，或退回暫存
        └── /tags        整理標籤庫（合併、改名、刪除、隱藏）
```

### 最關鍵的一個模型：一個檔名，兩種資源

`photo.png` 同時是磁碟上的檔案、也是 db.json 裡的一筆紀錄，**兩者生命週期分開**：

| 動作 | 檔案 | 紀錄 |
| --- | --- | --- |
| 上傳 | 建立 | — |
| 提交 | — | 建立 |
| 退回 | — | 刪除 |
| 永久刪除 | 刪除 | 必須已不存在 |

這個切分往上貫穿到 API（`/api/files` vs `/api/records`）、往下貫穿到模組
（`$lib/image` vs `$lib/database`），是整份架構的起點。
「暫存區」不是一種實體，只是「沒有紀錄的檔案」這個**篩選**。

## 二、分層總覽

```
                     ┌─────────────────────────────────────────────┐
   瀏覽器             │  src/routes/<page>/                          │
                     │    +page.svelte  logic/*.svelte.ts  body/*   │
                     │    ↑ controller 架構（context 注入）           │
                     │  src/lib/components/  src/lib/utils/*.svelte │
                     └───────┬──────────────────────┬──────────────┘
                             │ load (SSR，不走 HTTP) │ fetch（$lib/utils/request）
                             ▼                      ▼
                     ┌──────────────┐      ┌────────────────────────┐
   Node 伺服器        │ +page.server │      │ src/routes/api/**      │
                     │   .ts load   │      │   +server.ts（12 支）   │
                     └───────┬──────┘      └───────────┬────────────┘
                             └───────────┬─────────────┘
                                         ▼
        ┌────────────────────────────────────────────────────────────────┐
        │  $lib/query   $lib/mutation        ← 讀 / 寫兩個門面             │
        │        └──────┬──────┘                                          │
        │        $lib/database                ← 記憶體索引 + db.json 真相   │
        │                                                                 │
        │  $lib/image（檔案側，與 database 無 import 依賴）                  │
        │  $lib/collection（目錄與 server.json）                            │
        │  $lib/query-spec（同構值物件，前後端共用）                          │
        └────────────────────────────────────────────────────────────────┘
```

**依賴方向是單向的。** 三條值得記住的規則：

1. `$lib/image` 與 `$lib/database` **互不 import**。提交時需要的檔案側元資料
   （`fileSize` / `width` / `height` / `blurhash`）以結構相容的 `FileInfo` 型別傳遞，
   由端點居中轉手（[`image/metadata.ts:17`](../src/lib/image/metadata.ts#L17)）。
2. `$lib/query-spec` 是**同構**的：不 import 任何伺服器模組，前端拿它組查詢字串、
   後端拿同一個類別解析同一組查詢字串。這是「篩選條件」只有一份定義的原因。
3. `+page.server.ts` 的 `load` **直接呼叫 `$lib/query`，不經過 HTTP**。
   首屏資料一律走 `load`，不為了統一而改成 fetch 自己的 API。

## 三、伺服器生命週期

### 單例三兄弟

後端有三個模組層級單例，全部靠 `globalThis` 保存以撐過 Vite HMR：

| 單例 | 全域變數 | 綁定什麼 | 就緒判斷 |
| --- | --- | --- | --- |
| `Database` | `__db` | 一份 db.json | `Database.isLoaded()` |
| `ImageLibrary` | `__imageLibrary` | 一個 `images/` 目錄 | `ImageLibrary.isActive()` |
| `Collection` | `__activeCollectionRoot` | 收藏庫根目錄（純記憶體） | `getActiveRoot() !== null` |

（`Collection` 另有 `__collectionNameCache` 快取顯示名稱。測試就是靠清空這三個全域變數
來製造「伺服器剛啟動」的狀態測 503 守衛，見 [`test/api/fixtures.mjs:84`](../test/api/fixtures.mjs#L84)。）

### 啟動與引導

沒有 `hooks.server.ts` 的 `handle`——它只註冊 `SIGINT` / `SIGTERM`，在退出前 `Database.flush()`。
真正的啟動流程在 **根 layout 的 `load`**（[`+layout.server.ts`](../src/routes/+layout.server.ts)），
而且刻意分成寬鬆與嚴格兩條路：

```
                     ┌─ url 以 /settings 開頭 ─→ loadSettings()
url.pathname ────────┤                            root 未設定也照樣回傳，設定頁永遠可達
                     └─ 其他所有路由 ────────→ loadOther()
                                                 root 未設定 → 303 /settings?alert=default
                                                 root 無效   → 303 /settings?alert=error
                                                 正常 → setActiveRoot + ensureLoaded + ensureActive
```

也就是說：**任何一次對非設定頁的導航，都會順手確保三個單例就緒。**
各頁面的 `+page.server.ts` 仍再檢查一次 `Database.isLoaded()`，失敗同樣導向 `/settings?alert=error`。

`?alert=` 由 `/settings` 的 collection controller 解讀成畫面上的提示條
（[`settings/logic/collection.svelte.ts:23`](../src/routes/settings/logic/collection.svelte.ts#L23)）。

### 持久化節奏

寫入不是同步的。`Database.markDirty()` 標髒並排 **500ms 防抖**，
`flush()` 走 `.tmp` → `rename` 的原子寫入。強制 flush 的時機只有三個：
關閉訊號、備份前、載入另一份 db.json 之前。

載入時若主檔不存在但 `.tmp` 存在會自動升格復原；解析失敗則以空資料庫開始並立刻標髒
（[`database/store.ts:276`](../src/lib/database/store.ts#L276)）。

## 四、後端模組

### 4.1 `$lib/collection` —— 目錄與設定

最薄的一層。`Collection` 是一組靜態方法：

- **記憶體**：`getActiveRoot()` / `setActiveRoot()` / `nameOf()`（帶快取）
- **持久化**：`getPersistedRoot()` / `setPersistedRoot()` → `server.json`
- **結構**：`isValid()`（目錄存在？順手建 `images/`）、`paths()` → `{ root, images, db }`

刻意分成「記憶體的 active」與「磁碟的 persisted」兩件事：設定路徑是使用者的決定，
啟用路徑是這次執行的狀態，兩者由呼叫端自己接起來（見 `PUT /api/collection` 與根 layout）。

> `isValid()` **有副作用**（會建立 `images/`），因此 `GET /api/collection` 刻意不回傳 `valid`。

### 4.2 `$lib/database` —— 記憶體索引引擎

這是整個後端最有份量的部分。`Database` 同時是「db.json 的映射」與「查詢索引的宿主」，
但它自己不做業務判斷——它只提供原始讀寫與索引投影。

```
db.json  ──parseDBData──▶  DBData { version, images, tags }
                                │
                    rebuild()   │  每筆 ImageRecord
                                ▼
        OrdinalRegistry            FacetIndex
        id ⇄ 稠密序號               tagBits:    tag    → BitSet
        live: BitSet               tagCounts:  tag    → number（增量維護）
        墓碑刪除，過多時整體重建       sortedNames: 已用標籤的升冪名單（二分插入）
                                   ratingBits: 0..5 各一張 BitSet
```

四個檔案的分工：

| 檔案 | 職責 |
| --- | --- |
| [`bitmap.ts`](../src/lib/database/bitmap.ts) | `Uint32Array` 位元圖。AND / ANDNOT / OR / SWAR popcount，熱路徑 `andSize()` 融合 AND+popcount 不配置中間集合 |
| [`ordinal.ts`](../src/lib/database/ordinal.ts) | 字串 id ⇄ 序號雙向映射。序號**純記憶體、永不持久化**；刪除留墓碑，墓碑數 > 存活數時由 store 觸發整體重建 |
| [`facet-index.ts`](../src/lib/database/facet-index.ts) | 標籤與評分的位元圖維護。標籤位元圖惰性建立、空掉即刪；`sortedNames` 以 `sortCollator` 二分插入維持名稱序 |
| [`serialization.ts`](../src/lib/database/serialization.ts) | db.json 的解析與稀疏處理。逐筆寬容（壞紀錄跳過記 warn）；`TagMetaCodec` 負責「稀疏 ⇄ 完整」，全預設值不落地 |

資料版本目前是 **v2**（v1 沒有 `tags` 欄位，讀進來自動當空表）。`TagMeta` 目前只有 `hidden`。

索引維護的唯一入口是 `replaceIndex(id, oldRec)`，**呼叫端必須先寫好真相再呼叫**；
傳入的 `oldRec` 與索引現況矛盾時會記 error 並保守地整體 `rebuild()`。

### 4.3 `$lib/query-spec` —— 同構查詢值物件

前後端唯一共用的「篩選條件」定義。全部是不可變值物件，一律有 `with()` 做單層覆寫。

```
ImageQuery  = ImageWhere            + ListOptions<ImageSort>
              search / includedTags   sort / order / page / limit
              excludedTags            預設 rating desc、不分頁（limit 0）
              rating / ratingOp

TagQuery    = TagWhere              + ListOptions<TagSort>
              name / hidden           預設 count desc
              universe: used | all

TagFacetQuery = ImageWhere（當 scope）+ TagQuery
```

三個共通約定：

- `fromSearchParams(params)` 解析、`toSearchParams(base?)` 序列化，**自動略過預設值**讓網址精簡。
- 傳入 `base` 時會先深拷貝再刪掉自己的 `KEYS`，因此能保留頁面其他查詢參數（例如 `pinned`、`modal`）。
- 解析工具（`parseTags` / `safeInt` / `parseEnum` / `parseBool`）集中在 [`search-params.ts`](../src/lib/query-spec/search-params.ts)，
  無效值一律回 `undefined`，不讓 `NaN` 污染下游。

### 4.4 `$lib/query` —— 讀取門面

`new Query(db)` 內部組出 `ScopeResolver` + `ImageEngine` + `TagEngine`。

**`ScopeResolver` 是 hidden 語義的唯一權威**（[`query/scope.ts`](../src/lib/query/scope.ts)）：

> 設 H = hidden 標籤集合、Q = 查詢的 `includedTags`，
> 一張圖片被遮蔽 ⟺ 存在 h ∈ H 使該圖擁有 h 且 h ∉ Q。

也就是「明確查了某個隱藏標籤，它底下的圖片就現形」。解析結果同時回傳遮蔽前後兩份位元圖，
因為分面計數需要用到遮蔽前的集合。

圖片查詢管線：

```
live 全集
  → ∩ includedTags 各自的位元圖（任一不存在即空集）
  → ∖ excludedTags
  → ∩ ratingRange(gte/lte/eq 換算出的區間)
  → 名稱子字串後置過濾（位元圖表達不了，迭代候選再收斂回位元圖）
  → ∖ hidden 遮罩
  → materialize（序號 → 紀錄）→ 排序 → paginate
```

排序：`random` 走 Fisher-Yates；其餘以 `sortCollator`（`numeric: true` 自然排序）比較，
且**一律以名稱做 tiebreak**。

標籤查詢有兩個分支：

- `tags()` **獨立列表**：count = 全域原始使用數，不遮蔽。
- `facets()` **分面**：count = 目前 scope 內遮蔽後的可見數。對於「hidden 且不在 includedTags」
  的標籤，特別改用「把它自己加進豁免集後」的可見數——也就是**使用者點下去之後會看到幾張**，
  而不是 0（[`query/tags.ts:46`](../src/lib/query/tags.ts#L46)）。

`universe: "all"` 時會把「只有元資料、沒有任何圖片使用」的標籤（count 0）二分插入既有名稱序。

另外三個非清單查詢：`unionCount(tags)`（合併預估）、`tagCounts(names)`（逐一計數）、
`getAllImages()`（維護掃描用）。

### 4.5 `$lib/mutation` —— 寫入門面

`new Mutation(db)` 包住 `ImageCommands` 與 `TagCommands`。

**錯誤模型是純物件可辨識聯集**，不是例外（[`mutation/result.ts`](../src/lib/mutation/result.ts)）：

```ts
type Result<T, E> = { ok: true; data: T } | { ok: false; error: E }
type MutationError = NotFound | AlreadyExists | StaleUpdate | LastTag | Validation
```

`Validator` 是進門的第一道，所有命令的使用者輸入型別都是 `unknown`——**端點不預判、不補值**。

圖片命令：

| 方法 | 語意 |
| --- | --- |
| `commitRecord` | 建立，已存在 → `AlreadyExists` |
| `restoreRecord` | 建立或覆寫（匯入專用，語意是「以檔案為準重建」） |
| `updateRecord` | 以 `expectedUpdatedAt` 做**樂觀併發檢查**，不符 → `StaleUpdate` |
| `updateRecordFileMeta` | 只補 width/height/blurhash，不動 `updatedAt`、不影響索引（維護用） |
| `removeRecord` | 移除紀錄（= 退回），檔案不動 |

標籤命令的重點在 **`applyTagChanges(changes)`**：body 以標籤名為鍵，
所以「同一標籤同時只能有一種操作」是結構保證。內部固定執行順序 **刪除 → 改名 → 顯隱**，
並先做一輪集合層檢查（改名目標若同時被刪除或本身也要改名，該筆單獨驗證失敗、其餘照常執行）。

兩個值得記的不變量：
- `deleteTag` 會先掃一遍，**任何圖片都不得因此失去最後一個標籤**，否則回 `LastTag` 並帶受影響的 id。
- `renameTag` 指向既有標籤即是合併；元資料一併搬移，目標已有設定時遵從對方。

改名與刪除影響面廣，完成後直接 `db.rebuild()` 而不是逐筆維護索引。

### 4.6 `$lib/image` —— 檔案側

模組外部只允許 import 兩個入口：`server.ts`（Node）與 `client.ts`（瀏覽器）。

`ImageLibrary`（server）的能力：

- `list()` 列出支援副檔名的檔案（自然排序）、`has()` / `resolve()`（含**路徑穿越檢查**）
- `probe()` → `FileInfo`（檔案大小 + 寬高 + BlurHash）
- `payload(file, size, animated)`：`xl` 走原檔串流，`sm`/`md` 走 WebP 縮圖 buffer
- `clear()` / `stats()` 縮圖快取

內部由 `ImageProcessor` 負責產生縮圖：**LRU 快取（512 MiB 上限）+ 併發池（4）+ in-flight 去重**，
快取鍵含 `size` 與是否動畫。`sm` ≤ 512×512、`md` ≤ 1024×1024，且優先用整數倍比例縮放
以避免比例誤差（退化時才 fallback 到連續比例）。

兩個特別的實作決定：

- 檔案頂端 `sharp.cache(false)`：libvips 原生快取會在 Windows 鎖住剛產過縮圖的檔案，
  導致刪除時 `EBUSY`/`EPERM`。本模組自己有 LRU，關掉它影響可忽略。
- `blurhashStyle({ fit: "contain", ... })` 會多包一層 SVG 用 `preserveAspectRatio="none"`
  強制拉伸，數學上消除「blurhash 點陣尺寸被四捨五入」造成的殘影
  （[`image/blurhash.ts:72`](../src/lib/image/blurhash.ts#L72) 有完整推導）。

client 端只導出 `imgSrc(file, size?, animated?)` 與 `blurhashStyle`。
`imgSrc` 指向 `/api/files/{name}`——要的是磁碟上那個檔案的內容，
**與它有沒有紀錄無關，所以暫存與已提交共用同一組 URL**。

## 五、HTTP API 層

12 支端點，完整規範見 [`svelte_kit_api.md`](./svelte_kit_api.md)。這裡只列骨架與最需要記住的幾條：

```
/api/collection           GET  PUT           圖片集設定（唯一不需要就緒守衛的資源）
/api/collection/backup    GET                以 ZIP 取得整個圖片集
/api/cache                GET  DELETE        縮圖快取（也沒有守衛）

/api/files                GET  POST          實體檔案：分群列出 / multipart 上傳
/api/files/[name]         GET  DELETE        二進位內容 / 永久刪除

/api/records              GET POST PUT PATCH 已提交紀錄：查詢 / 批次提交 / 批次匯入(SSE) / 批次更新
/api/records/[id]         GET POST PUT PATCH DELETE

/api/tags                 GET  PATCH         分面查詢 / 批次異動
/api/tags/counts          POST               一組標籤的計數摘要（counts + union）
/api/tags/[name]          GET  PATCH DELETE

/api/maintenance/orphans   GET DELETE        有紀錄、檔案卻不存在
/api/maintenance/metadata  GET PATCH         缺 blurhash 或寬高
```

- **成員層與集合層是同一組動詞**，集合層對多筆做。批次 body 一律 `{ "<id>": <成員層 body> }`，
  回應 `{ "<id>": { ok } }`，鍵與請求完全對齊。集合層 `PATCH` 的 `null` ≡ 對該成員 `DELETE`。
- **成功回資源本身，沒有 `{ ok, data }` 封包**；失敗一律 `error(status, message)`，
  body 恆為 `{ message }` 且訊息已是人類可讀中文。
- **`MutationError → {狀態碼, 訊息}` 的對映只有一份**，在 `$lib/utils/server.ts`
  （`throwMutationError` 給單筆、`mutationMessage` 給批次）。
- **就緒守衛每支自己寫**，刻意不抽共用助手：這段檢查同時碰三個模組，抽出去會讓
  「圖片集是否就緒的權威是誰」變模糊。這條判準（權威來源 ≥ 2 個模組就重複寫）也適用於其他地方。
- 兩個形狀例外：`POST /api/files` 用陣列回報（上傳當下沒有可當鍵的欄位），
  `PUT /api/records` 回 SSE（匯入動輒數千筆，必須邊做邊回報）。

## 六、前端架構

### 6.1 殼層

[`+layout.svelte`](../src/routes/+layout.svelte) 只做三件事：套 `app.css`、
掛 Header 與導航 Modal、掛五個**全域單例元件**——
`ConfirmDialog` / `Tooltip` / `ToastStage` / `ToastList` / `NavigationIndicator`。

這五個是用 `window` CustomEvent 溝通的，所以任何深度的程式碼都能直接呼叫：

```ts
addToast({ message: "已提交 3 張圖片", variant: "success" });      // toast-events.ts
const yes = await requestConfirm("確定要永久刪除？", { ... });      // confirm-events.ts
```

`/player` 會隱藏 Header（`fullscreen` 判斷）。主題由 `app.html` 的 inline script
在首次繪製前從 localStorage 決定，避免閃爍。

### 6.2 頁面的 controller 架構

**每個路由 = `+page.svelte` + `logic/`（controller）+ 若干純元件資料夾。**

```
routes/<page>/
├── +page.server.ts      load：直接呼叫 $lib/query，不走 HTTP
├── +page.svelte         只做兩件事：依相依順序呼叫 create*Context()、掛 window 事件
├── logic/
│   ├── page-data.svelte.ts   把 load 的 data 包成 getter context（每頁都有，內容幾乎逐字相同）
│   └── <domain>.svelte.ts    controller：狀態 + handle*，型別多半不 export
└── body/ header/ panel/ …    純元件：getContext 取狀態、事件接 handle*
```

四條原則（詳見 [`svelte_kit_routes_controller.md`](./svelte_kit_routes_controller.md)）：

1. **刻意簡單化**：一個 controller 要能用一句不含「以及」的話說完。
2. **正交**：`+page.svelte` 裡 `create*Context()` 的排列**就是依賴圖**，排不出線性順序代表邊界畫錯。
3. **不重複權威來源**：同一事實只有一個計算點。可機械檢查的推論是——
   **controller 之間可以呼叫彼此的公開 `handle*`，但不可以寫彼此的欄位。**
4. **最少暴露**：所有草稿寫入走同一個 private `mutate()`，不變式無法被繞過；
   單張與批次共用同一條路徑（handler 一律吃 `string[]`，單張傳 `[id]`）。

投影（把多個 controller 的狀態組成畫面形狀）**屬於模板不屬於 `logic/`**，
寫成元件裡的 `$derived`，不 export、允許重複。

### 6.3 URL 即狀態

前端狀態有一大半住在網址上。`$lib/utils/search-params.svelte.ts` 提供四個類別，
差別在「單一鍵 vs 一組鍵」×「真導航 vs 淺路由」：

| | 真導航（會重跑 `load`） | 淺路由（不重跑） |
| --- | --- | --- |
| 單一鍵 | `SvelteSearchParam` | `SvelteShallowParam` |
| 一組鍵 / 值物件 | `SvelteSearchParams<T>`（吃 `{parse, serialize}` codec） | `SvelteShallowParams<T>` |

真導航版本內建 **echo 緩衝**：記住自己上次送出的值，只有 URL 變化不等於它時才視為外部變動
（上一頁／下一頁／別人改連結）。沒有這層，連續輸入或多欄位各自 `goto` 會互相覆蓋。

淺路由版本不需要 echo（`replaceState` 是同步的），純可覆寫的 `$derived` 就夠。

**兩條全專案硬性規則**（原因見 [`svelte_kit_routes.md`](./svelte_kit_routes.md) 的「淺路由與 goto」）：

- 頁面上一旦發生過 `pushState`/`replaceState`，`page.url` 就與瀏覽器網址永久脫鉤。
  因此**對自身導航時第一個參數一律從 `location` 取**，不從 `page.url`。
- **禁用 `invalidateAll()` / `invalidate()`**——它們內部固定用 `page.url` 重跑。
  一律改寫成 `goto(location.href, { replaceState: true, invalidateAll: true, ... })`。
  全專案的「重新整理」都是這一行。
- 例外：`beforeNavigate` 裡判斷是否離開本頁**必須**用 `page.url.pathname`，
  因為 popstate 時 `location` 已經是目標頁。

實際用法舉例：

| 頁面 | 參數 | 類型 |
| --- | --- | --- |
| `/`、`/committed`、`/compare` | 整個 `ImageQuery` | `SvelteSearchParams`（真導航） |
| `/tags` | 整個 `TagQuery`（含頁碼） | `SvelteSearchParams`（真導航） |
| `/` | `modal`（詳情開哪張） | 手寫的淺路由 echo（[`(home)/logic/detail.svelte.ts`](../src/routes/(home)/logic/detail.svelte.ts)） |
| `/committed` | `currentId`（編輯面板開哪張） | `SvelteShallowParam` |
| `/compare` | `pinned`（釘選清單） | `SvelteShallowParams<string[]>` |
| `/settings` | `#section-*` + `page.state.activeHash` | scroll-spy，見 `nav.svelte.ts` |

### 幾個值得單獨說明的設計

**`staged` 與 `committed` 是同構但不共用的。** 資料夾、controller 名稱、大部分檔案逐字相同，
但兩處刻意各寫一份：`tag-impact`（committed 需要淨變化 delta 才能算出孤兒標籤，
staged 只會新增所以 35 行就夠）與 `Panel*Fields` / `PanelFooter`。

**「審查清單」是一個跨四頁的共同概念**（staged / committed / tags / tags-cleanup）。
每頁的 `review.svelte.ts` 形狀幾乎一樣：`SveltePagination` 切成每批 25 筆、
三態全選框、`checkableOf()` 判斷可否送出、`handleSubmit` 後只清成功項目的勾選。
**`review.totalCount` 同時是離頁守衛的依據**，所以那個欄位上註明「不可加入任何過濾」。

**快照機制（committed 專有）。** 編輯已提交圖片需要「原始值」來算 diff 與樂觀併發的
`expectedUpdatedAt`，但 `drafts` 與 `reverts` 都可能持有同一個檔案。
`snapshots.svelte.ts` 因此做成**引用計數**：`acquire(file, owner)` / `release(file, owner)`，
所有持有者放手才刪除快照。

**標籤影響評估。** staged / committed 的 `tag-impact` 與 tags 的 `merge-count` 都是
「輸入變動 → debounce 300ms → 打 `POST /api/tags/counts` → 用流水號作廢過期回應」的形狀。
走 POST 而非 GET 是因為名稱可能上百個，會先撞上 Node 的 header 長度上限。

**清理建議引擎**（[`tags/cleanup/suggestions.ts`](../src/routes/tags/cleanup/suggestions.ts)）
是唯一一段跑在 `load` 裡的重運算：共現矩陣、正規化分組、編輯距離 1（首字分桶）、
Jaccard 相似度、冷門與零使用標籤。它每 20,000 次內層操作就 `setImmediate` 讓出事件迴圈，
避免卡住同時進來的其他請求。

**播放器引擎**（[`player/logic/player.core.ts`](../src/routes/player/logic/player.core.ts)）
刻意是**非響應式**的純類別：自己跑 rAF、自己算佈局與無限捲繞複本、
只透過兩個 callback 把可見項目與進度推回 Svelte。長按加速、跳張、拖曳進度都在引擎裡。

## 八、三條典型資料流

### (1) 首屏瀏覽

```
瀏覽器  GET /?includedTags=風景&rating=4
   │
   ├─ +layout.server.ts load ─→ Collection/Database/ImageLibrary 就緒（或 303 到 /settings）
   │
   └─ (home)/+page.server.ts load
         ImageQuery.fromSearchParams(url.searchParams)
              ↓
         new Query(db).images(spec)
              ScopeResolver → 位元圖交集 → hidden 遮罩 → materialize → 排序 → paginate
              ↓
         { items, total }  ──→ createPageDataContext(() => data)
                                      ↓
                              MasonryWall 的 Virtualizer.masonry 只渲染可視項目
                                      ↓
                              每張 <img src={imgSrc(id, "sm")}> → GET /api/files/xxx?size=sm
                                                                    → ImageProcessor（LRU / 池 / 去重）
```

### (2) 在 `/staged` 批次提交

```
使用者編輯 → drafts.handleSetTags([...]) …（純本地，偏離基準才建立草稿，回到基準自動捨棄）
   │
   ├─ ReviewTrigger 徽章 = review.totalCount（也是離頁守衛的依據）
   │
開啟審查清單 → review.handleOpen()：清失敗匯總、跳第一批、預先勾選可送出項
   │            └─ tag-impact 同步 debounce 查 /api/tags/counts → 顯示「會新增哪些新標籤」
   │
按下送出 → review.handleSubmit() → submit.handleSubmit(files)
                 POST /api/records  { "a.png": { name, tags, rating }, ... }
                        └─ 每筆：isSafeFilename → isImageFile → has → probe → mutation.commitRecord
                 ← { "a.png": { ok: true }, "b.png": { ok: false, message } }
                 成功的 drafts.handleDiscardDraft() + toast
                 goto(location.href, { invalidateAll: true })  ← 重跑 load，清單自動縮短
                        └─ pointers/selection 因清單變動自動回落
```

### (3) 在 `/tags` 送出一批標籤異動

```
拖曳標籤 → drag.handleDrop(target) → zones.handleAssign(target, tags)
                                       （被拖的在選取中就整組放，否則只放它自己）
   │
zones（誰在哪一區）→ changeset（扁平成每標籤一筆 TagChange + problemOf 檢查）
                        └─ merge-count 對每個合併區 debounce 查 union 張數
   │
review 分批勾選 → submit.handleSubmit(names)
     PATCH /api/tags  { "舊名": { name: "新名" }, "冗名": null, "私密": { hidden: true } }
            └─ Mutation.applyTagChanges：集合層衝突檢查 → 刪除 → 改名 → 顯隱
     ← { "舊名": { ok: true }, ... }   成功的 zones.handleDetach() + goto(invalidateAll)
```

| `records-write` | 25 | 四個動詞、**寬高來自實際檔案而非請求**、POST 重複 409、PATCH 樂觀併發 409、DELETE 後實體檔案仍在 |
| `records-batch` | 20 | keyed map 鍵完全對齊、部分成功、`null` = 退回、**重複鍵只留最後一個**、SSE 的 progress/done 事件 |
| `tags` | 33 | 分面查詢帶 scope、批次三種操作同時送、兩種集合層衝突、合併去重、成員層三個動詞 |
| `tags-counts` | 12 | counts + union、hidden 不影響全域計數、名稱正規化與非法值略過 |
| `maintenance` | 15 | 孤兒紀錄與缺元資料的檢查／修復，以及「補不了的仍留在待修清單」 |

### 執行時間

全套跑完約 **2.3 秒**（`npm run test` 因為 npm 的包裝再多約 0.6 秒）。
以下是實測數字，取 3 次的中位數：

```
npm run test               ≈ 2.9 s   ← 平常敲的那一行
node ./test/run.mjs        ≈ 2.3 s   ← 扣掉 npm 包裝
node ./test/run.mjs 空跑    ≈ 0.39 s  ← 過濾掉全部 suite，只有 Vite server 啟停
```

拆開來看各領域（每個數字都含 0.39 s 的固定啟動成本）：

| 指令 | 耗時 | 扣掉啟動後 | 內容 |
| --- | ---: | ---: | --- |
| `run.mjs __nomatch__` | 0.39 s | — | Vite server 起停 + 暫存目錄 |
| `run.mjs virtualize` | 0.44 s | 0.05 s | utils 領域整個（33 條） |
| `run.mjs formats` | 0.56 s | 0.17 s | image fixtures + 32 條純函式斷言 |
| `run.mjs bitmap` | 1.19 s | 0.80 s | **repo fixtures 載入 9 個模組** + 22 條 |
| `run.mjs hidden` | 1.19 s | 0.80 s | 同上 fixtures + 27 條（斷言本身近乎免費） |
| `run.mjs mutation` | 1.35 s | 0.96 s | 同上 fixtures + 164 條（每條約 1 ms，rename/delete 會整體 rebuild） |
| `run.mjs processor` | 1.34 s | 0.95 s | image fixtures + **24 條真的用 sharp 編碼** |
| `run.mjs maintenance` | 1.35 s | 0.96 s | **api fixtures 載入 12 支端點 + 5 個模組**、合成 PNG |
| `run.mjs`（全部） | 2.30 s | 1.91 s | 830 條 |

結論很清楚：**時間幾乎全花在模組載入與 sharp 編碼上，830 條斷言本身只佔一小部分。**
`hidden` 與 `bitmap` 的耗時完全相同（都是 1.19 s）就是最好的證據——
兩者差 5 條斷言，但都要付同一份 repo fixtures 的 0.80 s。

實務上的意思是：**加測試幾乎不會讓測試變慢，除非它要 sharp 編碼真的圖片。**
反過來，用關鍵字過濾只跑單一 suite 也省不了多少（下限就是 0.4～1.2 s），
過濾的價值在輸出乾淨、不在速度。

> 量測環境：Intel i7-10510U（8 邏輯核心）／16 GB RAM／Node v22.19.0／Windows 10，
> 檔案快取已暖。冷開機首次執行會更慢（Vite 要重新轉譯）。

### 幾個關鍵決定

- 每個領域一支 `fixtures.mjs`，回傳工具物件 `h`；suite 只接 `(t, h)`，每個案例各自建 fixture。
- 落地檔一律進 `tmpRoot`。唯一逃出去的是專案根的 `server.json`（路徑寫死在
  `collection/config.ts`），由 `dispose()` 一併刪除。
- **`api` 領域排最後**：它會清空 `__db` / `__imageLibrary` / `__activeCollectionRoot`
  來測未就緒守衛，不該影響其他領域。
- 端點的邏輯就寫在 handler 裡，不做「導出函式再由 `GET` 呼叫」的間接層——
  handler 只用到 `RequestEvent` 的 `url` / `params` / `request`，測試自己捏一個就夠。
  `h.call()` 會把 `error()` 擲出的 `HttpError` 攤平成 `{ status, body }`，
  因此成功與失敗在測試裡是同一個形狀。
- **業務規則在 `test/repo/` 測，`test/api/` 只測「HTTP 這層有沒有接對」。**
  最明顯的例子是標籤批次：執行順序與集合層衝突的完整矩陣在 `mutation/tag-changes`（39 條），
  `api/tags` 只確認端點有把結果轉成對的 keyed 回應。
